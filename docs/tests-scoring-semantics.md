# Э3 — Семантика скоринга: как считает оригинал и как должны считать мы

Снято с `tests_app` (`lib/services/test_service.dart`, `summary_service.dart`) 27.07.2026. Эталонная реализация — `tools/tests-import/reference-scoring.mjs`, golden-фикстуры — `out/fixtures/`. Это спецификация, которую обязан воспроизвести TS-движок в Э4.

---

## Два независимых слоя

Скоринг разделён надвое, и это разделение стоит сохранить:

1. **Слой факторов** — проценты по шкалам самого теста (`secure`, `anxious`, `avoidant`, `fearful`). Из них выбирается профиль результата. Живёт внутри одного теста.
2. **Слой психологических шкал** — вклад каждого вопроса в 197 сквозных шкал через веса. Живёт поперёк всех тестов и кормит сводный портрет.

Слои считаются из одних и тех же ответов, но по разным правилам и не зависят друг от друга. Слой шкал в оригинале написан аккуратно; слой факторов содержит два дефекта, описанных ниже.

---

## Слой шкал (переносим как есть)

`ScaleScoreAccumulator` в `test_service.dart`. Формула на каждый вопрос с весами:

```
normalized = (answer − min) / (max − min)        // min/max берутся из ответов самого вопроса
directed   = weight < 0 ? 1 − normalized : normalized
weighted[scale]    += directed × |weight|
maxWeighted[scale] += |weight|

score[scale] = clamp(weighted / maxWeighted × 100, 0, 100)
```

Три свойства, ради которых это работает:

- **диапазон берётся из вопроса**, а не из таблицы констант, поэтому шкалы 0–4 и 1–5 обрабатываются одинаково верно;
- **знак веса = направление**, а не величина: отрицательный вес переворачивает нормализованный ответ, в накопление идёт модуль. Именно поэтому в Э2 знаки сохранялись, а `invert: true` их переворачивал;
- **делитель — сумма весов**, а не гипотетический максимум, так что вес 1.5 просто весит больше, и обрезать его не нужно.

Реверсию вопроса (`isReversed`) этот слой намеренно **не** применяет: направление уже закодировано в знаке веса, инвертировать дважды — вернуться к исходному.

## Слой факторов (переносим с исправлениями)

Формула оригинала:

```
raw[factor]  += answer.score            // без вычитания минимума
max[factor]  += maxQuestionScore        // константа из таблицы по id теста
percentage    = raw / max × 100
```

Здесь два дефекта.

### Дефект 1: `maxQuestionScore` — таблица констант вместо данных

В `test_service.dart` (строки 117–165) максимум задан вложенным тернарником на 25 уровней, по одному на id теста, со значением по умолчанию 5. **13 тестов из 43 в таблице отсутствуют, хотя их шкала 0–4**, и их проценты считаются от 5.

Из запускного набора это `toxic_patterns`. Следствие проверяемое: пользователь, ответивший «Постоянно» на все 48 вопросов, получает 4/5 = 80%, а не 100%. А выбор профиля в этом тесте устроен так:

```dart
} else if (overallToxicity <= 80) {
  return 'high_toxicity';      // 66-80%
} else {
  return 'severe_toxicity';    // 81-100%
}
```

Потолок ровно 80%, ветка требует больше 80 — **профиль `severe_toxicity` недостижим ни при каком наборе ответов**. Полностью написанный профиль с ru/en контентом, который не увидит ни один пользователь.

Помимо `toxic_patterns` затронуты: `attention_style`, `burnout_diagnostic_v1`, `conflict_communication_style_v1`, `dark_personality_traits`, `gaming_balance_check_v1`, `mental_age_lifespan_styles_v1`, `money_mindset_habits_v1`, `romantic_potential_v1`, `self_esteem_test`, `self_sabotage_how_you_block_yourself_v1`, `social_battery_v1`, `stress_test`.

**Исправление:** максимум выводится из ответов вопроса, как в слое шкал. Никакой таблицы по id.

### Дефект 2: обратные вопросы не инвертируются

Реверсия применяется только для двух тестов:

```dart
if (question.isReversed) {
  if (test.id == 'ipip_big_five') { score = 6 - selectedAnswer.score; }
  else if (test.id == 'love_profile') { score = 6 - selectedAnswer.score; }
}
```

Для остальных `isReversed` в данных есть, но в расчёте игнорируется: **22 теста, 247 обратных вопросов**. Из запускного набора это `friendship_red_flags_v1` (6 вопросов).

Что это значит содержательно. Вопрос q13 «Когда я вымотан, я могу честно сказать друзьям, что мне нужен отдых» помечен обратным к фактору «трудность с границами». Ответ «Всегда» должен означать, что границы **в порядке**, а начисляется +4 к трудности с границами. Прямые и обратные пункты складываются в одну кучу, и фактор перестаёт что-либо измерять.

**Исправление:** зеркалим внутри собственного диапазона вопроса — `min + max − score`. Это обобщение оригинального `6 − score`, которое верно и для 0–4, и для 1–5.

### Дефект 3: часть весов не доезжает до пофакторного расчёта

Обнаружен уже в Э4, при сверке движка с фикстурами. У `attachment_styles_v1` двенадцать вопросов имеют по два-три набора весов под разными ключами карты: `attachment_styles_v1:q1`, `:q1_bipolar`, `:q1_bipolar_f` — при одинаковом `questionId: 'q1'`. Дополнительные наборы добавляют вклад в биполярные полюса.

Оригинал видит их по-разному в двух своих путях. Пофакторный расчёт зовёт `getWeights(testId, questionId)`, то есть ищет ровно ключ `:q1` и находит только базовый набор. Сборка типа личности перебирает все ключи по префиксу и видит все три. То есть один и тот же вопрос вносит разный вклад в зависимости от того, кто спрашивает.

**Исправление:** наборы объединяются по `questionId` — они для того и написаны, чтобы применяться вместе.

### Итоговая формула слоя факторов

```
score = question.isReversed ? (min + max − answer.score) : answer.score
raw[factor] += score − min
max[factor] += max − min
percentage   = raw / max × 100
```

Вычитание минимума добавлено, чтобы шкала 1–5 давала 0% за все минимальные ответы, а не 20%.

## Биполярный слой (тип личности)

`sixteen_types` и всё, что несёт веса на 8 полюсов, идут отдельным путём: `summary_service.calculateAveragedPersonalityType`. Полюса накапливаются как обычные шкалы, но результат **не читается по абсолютной величине** — только сравнением внутри пары.

Это видно на фикстуре: при согласии со всеми 80 утверждениями `extraversion` и `introversion` оба равны 100. Осмысленный ответ даёт только пара: в фикстуре `ladder` выходит E=40 против I=60, то есть интроверсия.

```
percentage(EI) = E / (E + I) × 100      // и так же для SN, TF, JP
буква          = percentage > 50 ? первый полюс : второй
```

Тип собирается из **всех** пройденных тестов, а не только из `sixteen_types` — поэтому он и есть основа SKU «сводный портрет».

## Частные схемы скоринга

Каноническая схема Э4 обязана нести их как тип теста, а не как ветку `if` по id:

| Схема | Где | Как считается |
|---|---|---|
| Likert по фактору | большинство | описано выше |
| **Фактор в ответе** | `conflict_communication_style_v1`, `digital_career_fit_v1`, 8 вопросов `creative_type_v1` | `factorId` вопроса = `multi_choice`, а `score` варианта — это **индекс** фактора в `factorOrder`. Выбор даёт +1 своему фактору; суммировать баллы нельзя |
| Сценарная | `text_conflict_communication` | ситуация + контекст + вопрос + 4 варианта, каждый вариант привязан к стилю. Механика та же, что «фактор в ответе», но карточка другая |
| Ипсативная | `career_compass_v1` | 56 парных сравнений, баллы перераспределяются между шкалами |
| Бинарная | `cognitive_ability_v1` | правильно/неправильно, максимум 1 |
| Накопление черт | `visual_micro_tests_v1` | каждый выбор добавляет очки набору черт, показываются топ-5 |

Из запускного набора частная схема нужна одна — сценарная, для флагмана.

## Выбор профиля живёт в коде, а не в данных

`determineProfile` у каждого теста — это Dart-функция, и её нельзя достать экстрактором. Форм две:

**Порог по среднему** (`friendship_red_flags_v1`, `toxic_patterns`):

```dart
final avg = percentages.values.reduce((a, b) => a + b) / percentages.length;
if (avg >= 75) return 'profile_high_risk';
if (avg >= 50) return 'profile_elevated_risk';
...
```

**Цепочка правил по нескольким факторам** (`attachment_styles_v1`):

```dart
if (secure > 70 && anxious < 30 && avoidant < 30 && fearful < 30) return 'secure';
if (anxious > 60 && anxious > avoidant && anxious > fearful) return 'anxious';
...
```

Обе формы описываются данными: упорядоченный список правил, каждое — набор условий вида «фактор ⋛ число» или «фактор ⋛ другой фактор», плюс профиль по умолчанию. **Задача Э4: перенести эти правила в JSON вручную по каждому взятому тесту** — их семь, это обозримо, но пропустить нельзя: без правил тест выдаёт проценты и ни одного профиля.

---

## Решение: чиним, а не воспроизводим

Оба дефекта исправляются, поведение оригинала не сохраняется. Обоснование: сохранять нечего — накопленных результатов пользователей нет, обратной совместимости не требуется, а воспроизводить занижение процентов и недостижимый профиль смысла нет.

Следствие: числа нашего движка **не будут совпадать** с числами Flutter-приложения на тех же ответах. Это ожидаемо и правильно. Сверять надо с фикстурами, а не со старым приложением.

## Golden-фикстуры

```bash
node tools/tests-import/reference-scoring.mjs
```

Кладёт в `out/fixtures/<test_id>.json` по четыре детерминированных набора ответов на каждый тест запускного набора — `all_min`, `all_max`, `middle`, `ladder` — с ожидаемыми процентами по факторам и оценками по шкалам. Случайности нет, фикстуры стабильны между прогонами.

Что они фиксируют (и что должно сойтись в Э4):

| Тест | `all_max` по факторам | Что проверяет |
|---|---|---|
| `attachment_styles_v1` | 100% | базовый Likert без обратных вопросов |
| `toxic_patterns` | 100% | исправленный максимум: в оригинале было бы 80% |
| `friendship_red_flags_v1` | 66.7–83.3% | исправленную реверсию: в оригинале было бы 100% |
| `ipip_big_five` | 20–70% | реверсию на 24 вопросах (единственный тест, где оригинал делал это верно) |
| `love_languages_v1` | 100% | шкалу важности 0–4 |
| `sixteen_types` | полюса по 100 | что пары полюсов нельзя читать по модулю |

`text_conflict_communication` в фикстурах отсутствует: у него кастомная форма данных, эталон для него пишется в Э4 вместе со схемой сценарных тестов.
