# Фундамент: спеки тестов + робот-тестировщик

Статус: заложено 31.07.2026 вместе с независимым аудитом качества
(`docs/tests-quality-audit.md`). Цель — превратить «19 тестов, проверенных руками
при батч-деплоях» в систему, где у каждого теста есть проверяемая спецификация,
а робот сам генерирует данные и проверяет расчёты каждого теста и саммари.
Обновление 04.08.2026 (этап 3 аудита): уровень **L3 реализован** — пейлоад-билдеры
вынесены в `supabase/functions/_shared/`, снапшоты и инварианты фидов живут в
`tools/tests-audit/` (`feed-snapshot.mjs`, `feed-invariants.mjs`, README там же);
из «Порядка работ» закрыты вынос из Р1 и Р4 целиком.

Что уже существует и на чём строим:

- `tools/tests-import/verify-engine.mjs` + `fixtures/` — движок против golden-фикстур
  (4 детерминированных паттерна ответов × 18 тестов). Проверяет АРИФМЕТИКУ, но не
  правила профилей, не пороги, не контент, не фид LLM.
- `tools/tests-audit/` (новое, из аудита 31.07) — структурный аудит, персонная
  симуляция, разбор фида портрета. Это уровни L0/L2/L3 робота в зачаточном виде.
- Точечные «синтетики» из батч-деплоев (достижимость boundary_master и т.п.) —
  разовые, нигде не закреплены. Робот делает их постоянными.

## 1. Спека теста — шаблон

Одна спека на тест, файл `docs/test-specs/<test_id>.md`. Не пересказ JSON, а то,
чего в JSON нет: намерение, целевые распределения, инварианты. Робот читает
машинную часть спеки (front matter YAML) и проверяет против неё.

```markdown
---
id: attachment_styles_v1
scoring: likert
questions: 60
factors: [secure, anxious, avoidant, fearful]
# Целевое распределение профилей на реалистичной популяции (сумма ~100).
# Это ГЛАВНОЕ, чего сейчас нет: без целевого распределения нельзя сказать,
# «сломаны пороги или так задумано». Диапазоны — допуск для робота.
target_distribution:
  secure: 10-25
  anxious: 15-30
  avoidant: 15-30
  fearful: 10-25
  mixed: 15-35        # fallback: доля «смешанных» — осознанный продуктовый выбор
max_fallback_share: 35  # жёсткий потолок: больше — тест «не различает людей»
reachability: all       # каждый профиль достижим; исключения перечисляются явно
dead_profiles: []       # осознанно мёртвые профили — только явным списком
min_items_per_factor: 6 # надёжность: меньше — фактор считается ненадёжным
scale_contract:
  min_weight_items: 2   # шкала, живущая на 1 вопросе, в сквозной слой не идёт
free_tier: bars_free    # граница §2 tests-monetization
report_kind: spectrum
support_note: [fearful] # у каких профилей обязан быть supportNote
---
# Намерение
Что тест утверждает о человеке, откуда конструкты (типология привязанности),
что тест НЕ утверждает (не диагноз). Почему выбраны такие правила профилей.
# Известные компромиссы
60 вопросов — кандидат на сокращение по данным доходимости; secure требует
одновременно высокого secure и низких остальных — обоснование порога.
# История изменений порогов/весов
```

Порядок написания спек: сначала 4 теста с найденными в аудите дефектами порогов
(boundaries, EI, fomo, text_conflict), потом уровневые, потом остальные. Спека
пишется ЧЕЛОВЕКОМ (решения о целевых распределениях — продуктовые), робот её
исполняет. Черновики целевых распределений может предложить симуляция.

## 2. Робот-тестировщик — уровни

Принцип: робот сам генерирует нужные ему данные (ответы, персоны, сессии) и
проверяет всю цепочку «ответы → расчёт → профиль → фид LLM → (по флагу) сам LLM».
Один вход: `npm run tests:robot [-- --level 0..4 --test <id>]`.

### L0 — структура данных (быстро, на каждый PR)
Уже есть в `tools/tests-audit/audit.mjs`, доработать до exit code ≠ 0:
- index.json ↔ файлы ↔ регистрации (registry.ts, freeTier.ts, обе эдж-функции,
  REPORT_KIND) — один тест, зарегистрированный не везде, валит сборку;
- id/локализация/дубликаты/веса-сироты/ссылки правил на несуществующее;
- профили, на которые не ссылается ни одно правило (мёртвый контент), — ошибка,
  если не в `dead_profiles` спеки;
- факторы с числом вопросов < `min_items_per_factor`;
- **шаблонные плейсхолдеры в текстах** (`[...]`, `TODO`, `{{`) — аудит 31.07
  нашёл «[ресурс для микрозаймов/помощи]» в живом ответе флагмана;
- **реестр шкал**: каждый id веса обязан существовать в каноническом реестре
  (`tools/tests-import/scale-registry.json` — создать) с полем direction
  («высокое значение означает …»); ловит сироты типа `feelings` vs `feeling`
  и `values` с двумя семантиками.

### L0.5 — направленный линт весов (новый, по следам аудита 31.07)
Самый урожайный класс дефектов (attachment 0 минусов из 349, fomo-хвосты,
detox q15, ipip q2) ловится без ИИ тремя механическими проверками:
1. **Знак против ключёвки пункта**: если вопрос принадлежит фактору
   «проблемной» направленности (у уровневых тестов: высокий фактор = хуже) и
   isReversed=false, то позитивно-направленные шкалы реестра (trust, empathy,
   self_esteem…) могут стоять на нём только с минусом — и наоборот. Требует
   в реестре шкал поле polarity, в спеке теста — направление каждого фактора.
2. **Внутренняя согласованность**: одна шкала на двух пунктах одного фактора с
   одинаковой ключёвкой не может иметь противоположные знаки (ловит
   social_battery q20/q38 vitality, burnout prudence, detox q2/q9).
3. **Блочные дубликаты**: идентичный набор «шкала:вес» на ≥6 вопросах подряд —
   почти наверняка вклеенный хвост (ловит fomo).
Плюс один отчётный (не блокирующий) сигнал: доля отрицательных весов теста
= 0 при наличии негативно сформулированных пунктов — повод для ручного прохода.

### L1 — арифметика движка (есть)
`tests-import/verify-engine.mjs` как есть. Добавить: фикстуру для
`text_conflict_communication` (единственный без golden), и случай «частичные
ответы» (сервер принимает неполные answers — поведение должно быть зафиксировано,
а не случайно).

### L2 — геометрия правил и распределения (ядро робота)
Из `tools/tests-audit/audit2.mjs`, довести до вердиктов против спек:
- **достижимость**: каждый профиль вне `dead_profiles` достигается хотя бы одной
  сгенерированной персоной/пробой; иначе FAIL (сегодня это поймало бы
  `profile_moderate` у burnout и `profile_problematic` у detox);
- **распределение**: симуляция N=4000 персон против `target_distribution` спеки;
  выход за диапазон — FAIL (сегодня: 79.5% boundary_builder, 65.6% mixed у
  дружбы, 59.8% the_mixed у флагмана);
- **fallback-потолок** против `max_fallback_share`;
- **чувствительность**: смена одного ответа не должна перекидывать через два
  уровня (монотонность уровневых тестов);
- **ничьи**: пробы с точными ничьими факторов — результат детерминирован и
  задокументирован (сейчас решает порядок обхода Object.entries).
Модель персон калибруется: когда в `looplore_test_sessions` накопятся реальные
завершённые сессии, распределения симуляции сверяются с фактическими (см. L5) и
параметры персон (корреляции факторов, доля крайних ответов) подгоняются.

### L3 — фид LLM-слоёв (детерминированный, без вызова модели)
Самый дешёвый способ поднять качество разбора и портрета — тестировать ПЕЙЛОАДЫ.
Для этого `buildPayload` (tests-generate-report) и сборку `portraitInput`
(tests-portrait) вынести в чистые функции в `supabase/functions/_shared/` и
импортировать в робота. Инварианты:
- в пейлоаде нет сырых snake_case там, где обещаны имена; нет пустых секций;
- у биполярных тестов factor_percentages НЕ отправляются (сейчас sixteen_types
  шлёт {EI:0, SN:0, TF:0, JP:0} — мусор, который модель может прочитать как
  «крайняя интроверсия»);
- quote_candidate направлен по ФАКТОРУ, а не по сырому баллу (сейчас реверсивный
  вопрос с ответом «совершенно верно» помечается max при том, что по фактору это
  минимум, — модель получает противоречащий сигнал);
- у портрета: шкалы с межтестовым расхождением ≥ порога обязаны попадать в фид
  (сейчас 91% таких шкал отрезается сортировкой |score−50|, см. аудит §5);
- вклад шкалы от теста, где она живёт на < `min_weight_items` вопросах, в
  сквозной слой не идёт (шум одиночных пунктов);
- размер фида в токенах в бюджете (грубая оценка по символам).

### L4 — LLM-контракт (по релизам, с бюджетом)
Робот генерирует 3–5 контрастных персон на тест, зовёт настоящие функции
(стейдж-режим: `ROBOT_MODE=1` — без спенда, отдельная таблица/локальный вызов
модели) и проверяет LLM-judge'ем чек-лист:
- дословность цитат (каждая цитата в кавычках существует в answers);
- все числа в тексте существуют в фиде (модель не выдумала процентов);
- тон-рамка уровневых: нет диагнозов/ярлыков-существительных/назначений;
- главы соответствуют схеме по смыслу (throughlines реально называет
  противоречие, а не три гладких обобщения);
- у портрета: упомянутые тесты — из tests_taken, «чего не хватает» — из
  tests_not_taken.
Это единственный уровень, где робот тратит деньги; гонять на релиз функций и
при смене REPORT_MODEL/промптов, не на каждый PR.

### L5 — прод-дрейф (SQL, еженедельно)
Запрос к `looplore_test_sessions`: фактическое распределение profileId по
тестам против `target_distribution` спеки; доля straight-line сессий (все
ответы одинаковые); доля частичных. Расхождение → сигнал в чат/лог. Это
замыкает петлю: спека ← реальность, а не только симуляция.

## 3. Порядок работ (предложение)

1. **Р1 (день)**: L0 до exit-code + регистрация в CI (`npm run tests:audit`);
   вынос buildPayload/portraitInput в _shared (рефакторинг без изменения
   поведения, сверка байт-в-байт на фикстурных сессиях).
2. **Р2 (день-два)**: L2 против временных целевых распределений («не хуже
   сегодняшних» — зафиксировать текущие цифры симуляции как baseline, чтобы
   ловить регрессии до появления настоящих спек).
3. **Р3 (параллельно, порциями)**: спеки тестов — по 4–5 за заход, начиная с
   дефектных; каждая спека сразу включает target_distribution → L2 переключается
   с baseline на спеку.
4. **Р4**: L3-инварианты (после выноса пейлоад-билдеров).
5. **Р5**: L4 на пилотных 3 тестах (flagship + один levels + sixteen_types),
   бюджет ~$1–2 на прогон.
6. **Р6**: L5 SQL + недельный ритуал.

Пункты 1–2 не требуют продуктовых решений. Пункт 3 требует утверждения целевых
распределений основателем (это продуктовые решения о том, «сколько людей должны
получать какой результат»).

## 4. Открытые вопросы к основателю

- Целевые распределения: согласовываем ли принцип «fallback ≤ 35%» как дефолт
  для всех тестов? (Сейчас у 5 тестов fallback > 50%.)
- Мёртвые профили: чиним пороги, чтобы стали достижимыми, или вычёркиваем
  контент? (3 подтверждённых мёртвых + 4 практически мёртвых, список в аудите.)
- L4: допустим ли стейдж-вызов настоящих функций с ROBOT_MODE без спенда, или
  робот зовёт Anthropic API напрямую с теми же промптами (дешевле, но промпт
  может разойтись с прод-кодом)?
