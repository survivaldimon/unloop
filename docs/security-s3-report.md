## 1. Что изменено

### 1.1. Приватность: чтение сессий (пункты 1–2)

**Миграция `20260808140000_session_read_privacy.sql`** — приводит четыре
читающих anon-RPC к одному правилу:

> **UUID сессии — capability только пока сессия ничья.** Появился `user_id` —
> чтение требует JWT этого аккаунта.

Ровно это правило писчий путь тестов соблюдал с самого начала
(`looplore_test_session_save`/`_complete`, ветка `owned`) — теперь оно доехало
до чтения.

| RPC | Было | Стало |
|---|---|---|
| `unloop_get_session` | сырые ответы квиза любому обладателю UUID | владельцу — ответы; чужому — `{"locked": true}` |
| `looplore_test_session_get` | ответы + outcome по UUID | то же правило, тот же маркер |
| `looplore_chat_history` | вся переписка про психо-профиль по UUID | построчный гейт по `user_id` сообщения → чужому пустая история |
| `credits_session_state` | **полный баланс владельца** в каждом ответе | баланс только владельцу; всем — один бит `covered` |

**Почему `locked`, а не `null`.** Пустой ответ уронил бы человека по ссылке
`?s=` на пустой экран. Маркер даёт фронту повод предложить вход: квиз
(`src/App.tsx`) при `locked` ведёт на шаг почты в режиме «этот результат
сохранён в аккаунте — пришлём ссылку для входа», и слушатель `SIGNED_IN`
**повторяет восстановление** — по magic-link человек возвращается владельцем и
видит свой результат. Если после входа всё ещё `locked` — честная строка «это
результат другого аккаунта» вместо бесконечного круга. Копия EN+RU в `i18n.ts`.
Тесты (`loadTestSession`) трактуют `locked` как «строки нет» — `openFromLink`
уже умеет достраиваться из локальных ответов.

**Почему бит `covered`, а не просто «убрать баланс».** Пост-чекаутный поллинг
обязан работать и у покупателя **без сессии в браузере**: знакомый email →
magic-link → человек продолжает анонимно, а вебхук привязывает покупку по email
и **сам клеймит сессию** (`unloop-polar-webhook:~585`). Убери сигнал совсем —
оплаченный разбор не откроется. `covered` — это `balance >= 95`, ровно то, что
нужно пейволлу, и ничего больше. Порог продублирован в SQL с комментарием: это
подсказка пейволлу, реальное списание по-прежнему считается из
`credits-config.ts`, а `credits_spend` откажет недофинансированному аккаунту —
разъезд константы даёт максимум лишний показ пейволла, не бесплатный контент.

Фронт: `SessionCreditState.balance` стал `number | null`, `stateUnlocks`
использует точный баланс, когда он есть, и серверный вердикт, когда нет; чип
баланса не затирается чужим нулём (`App.tsx`, `photo/PhotoApp.tsx`).

**Что НЕ сломано (проверено по коду):** неклеймленные сессии (аноним до почты),
письма `?p=` (фото — `photoread_get_session` отдаёт только стадию, тизер и факт
оплаты, сужать нечего), `?ts=` (мнётся только в кабинете подписанному
пользователю — письмами не рассылается), кабинет (там всегда JWT), шеринг
результата (картинка на клиенте).

### 1.2. Prompt injection и косты (пункт 3)

`supabase/functions/unloop-generate-report/index.ts`:

- `session_id` — теперь проверяется на формат UUID (был единственным
  непроверенным идентификатором сессии во всём наборе функций) и нормализуется
  в нижний регистр — он же ключ идемпотентности списания.
- `quotes` — whitelist из пяти известных слотов, значения по 200 символов.
  Именно неограниченный размер `quotes` был управляемым ростом входных токенов
  Sonnet.
- `status`, `goal` — те же 200 символов.
- `anx`/`avo` — только конечные числа, клампятся в 0–100.
- `pattern`/`secondary` — lookup через `Object.hasOwn`: `"constructor"` больше
  не резолвится в объект прототипа.

Тесты и фото **не тронуты** — там в промпт идут каталожные тексты по answerId
(`_shared/report-payload.ts`), и это правильная схема; регрессировать её нельзя.

### 1.3. Мелкие серверные (пункты 4–6)

- **Meta CAPI-токен** — из query string в тело запроса (`unloop-polar-webhook`).
  Graph принимает оба, но именно URL-параметр оседает в логах и трейсах.
- **Валидация email в чекаутах** — все четыре (`credits-`, `subscription-`,

### 1.4. Ops-гигиена (пункты 8–9, 11)

**`.gitignore` + `.env.production` + CI-проверка.** Файл в git осознанно (все
значения публичны по замыслу), но `.gitignore` этого не объяснял и от реального
футгана не защищал. Теперь:

- `.gitignore`: `.env.*` под запретом с явным исключением `!.env.production`, и
  записано главное — **никогда не давать серверному секрету префикс `VITE_`**
  (Vite инлайнит их в бандл, и `.gitignore` тут бессилен);
- шапка-предупреждение в самом `.env.production`;
- `tools/check-bundle-secrets.mjs` (`npm run check:secrets`) — проверяет **оба
  конца** правила: env-файлы на `VITE_`-имя, звучащее как секрет (allowlist из
  трёх реально публичных), и собранный `dist/` на Supabase-JWT с ролью не `anon`
  плюс префиксы `sk-ant-`, `polar_oat_`, `whsec_`, `sbp_`. Блокирует CI.
  Проверен обоими способами: подложенный service_role-JWT и `VITE_*_TOKEN` в env
  ловятся, чистое дерево проходит.

**Деплой после зелёного CI.** `deploy.yml` триггерился на `push` в main
параллельно с `ci.yml` — красный main всё равно выкатывался. Теперь триггер —
`workflow_run` завершения CI на main с `conclusion == success`, а чекаут пинится
на `workflow_run.head_sha` (иначе на быстрой серии пушей выкатился бы не тот
коммит, что прошёл проверки). `workflow_dispatch` остаётся аварийным люком.

**Миграция `20260808130000_legacy_funnel_rpcs.sql`** — шесть RPC жили только в
проде: `unloop_save_session`, `photoread_save_session`, `unloop_get_paid_status`,
`photoread_get_paid_status`, `photoread_get_session`, `unloop_get_secret`. Сняты
с прода дословно (`pg_get_functiondef`), применение — no-op.

**Ревью, ради которого это заводилось:**

1. `*_save_session` пишут в сессию по голому UUID **без проверки владельца** —
   в отличие от писчего пути тестов. Отсюда и почтовый релей: `p_email` можно
   записать на чужую сессию. Паритетный гейт — правильный фикс, но он меняет
   поведение живой воронки и стыкуется с переделкой `unloop-send-result`,
   поэтому **намеренно оставлен S1**. Ограничители размера в них есть и работают.
2. `unloop_get_secret` — `EXECUTE` отозван у anon/authenticated (в проде ACL =
   postgres + service_role), `search_path = ''`. Ключевой факт безопасности
   всего проекта, нигде в репо не записанный. Теперь записан.
3. `*_get_paid_status` / `photoread_get_session` отдают по UUID только факт
   оплаты и бесплатный тизер — сужать нечего.

Сверено с живым продом: определения `credits_session_state`,
`looplore_chat_history`, `looplore_test_session_get` в проде **совпадают** с
репозиторными — мои переписывания ничего не откатывают.

### 1.5. Приватность аналитики (пункт 13)

Решение основателя: **привести потоки под текущий Privacy**, а не наоборот.

- `posthog.identify(sessionId, { email })` → `posthog.identify(sessionId)`.
  Адрес идёт только туда, куда Privacy обещает: письмо с результатом и Meta в
  виде SHA-256-хэша. Идентификация остаётся псевдонимной, person-профиль
  по-прежнему создаётся.
- **Паттерн квиза убран из аналитики целиком** — он был не только свойством
  событий PostHog, но и уезжал в **Meta** (`QuizComplete {pattern}` и
  `ViewContent content_name = <паттерн>`), чего Privacy не обещал вовсе. Убран
  из супер-свойств (`setAnalyticsContext`), из `quiz_complete`, `teaser_view`,
  `report_view`, `share` и из обоих Meta-событий. Сами события остались.
- Цена: срез воронки по паттернам в PostHog/Meta пропадает. Данные для него
  никуда не делись — `session_db_id` остаётся супер-свойством, и связка с
  `unloop_sessions.pattern` на своей стороне сохраняется.

## 2. Продуктовые решения основателя 07.08.2026

**Квиз-разбор: скелет бесплатный, персонализация платная** (пункт 7 —
зафиксировано как продуктовое решение, кода не требует).
Статический скелет разбора и generic-fallback главы лежат в клиентском бандле у
каждого посетителя, а `unlocked` — флаг в `localStorage`. Флип флага показывает
эту статику. Персональные LLM-главы (I «Твой личный разбор» и II «Как это
читается с их стороны») — за 402-гейтом `unloop-generate-report` и **не**
доступны без оплаты; тесты и фото так не умеют вовсе (у них весь разбор
серверный). Решение: не гейтить статику на сервере. Обоснование — контент
generic и всё равно скачан каждым, платная персональная часть уже защищена, а
серверный гейт был бы переделкой отложенной воронки ради generic-текста.
Известный побочный эффект: обещание тизера «шаги 3–5 запечатаны» для
флип-флагом обходится, но ничего персонального человек не получает.

**EU/UK в планах → нужен consent-баннер** (пункт 12 — **отдельная задача,
блокирует EU/UK-трафик в Э9**).
Сейчас PostHog и Meta-пиксель инициализируются безусловно при загрузке
(`src/lib/analytics.ts:24-43`) — для US/CA/AU это допустимо, для EU/UK это
нарушение GDPR/ePrivacy. Что нужно сделать отдельной сессией:
- баннер согласия (EN+RU) с равнозначными «принять»/«отклонить»;
- **отложенная** инициализация `posthog.init` и `initMetaPixel` — до согласия
  не грузить ни один из них (сейчас оба стартуют на верхнем уровне модуля);
- запись выбора и возможность его изменить;
- решить, что делать с `captureAttribution()` (utm/fbclid читаются из URL до
  всего остального).
До этого рекламу Э9 на EU/UK **не включать**.

## 3. Что требует «го»

Строго после S1 и S2 (решение основателя):

1. **Мерж ветки в main** → CI → Pages (деплой теперь сам дождётся зелёного CI).
2. **Две миграции** (в порядке номеров):
   - `20260808130000_legacy_funnel_rpcs.sql` — no-op, фиксация статус-кво;
   - `20260808140000_session_read_privacy.sql` — меняет поведение четырёх RPC.
   Обе `create or replace`, откат — переприменить предыдущие определения
   (они в этих же файлах / в `20260727120000` и `20260728160000`).
3. **Редеплой шести edge-функций**: `unloop-generate-report`,
   `unloop-polar-webhook`, `credits-polar-checkout`,
   `subscription-polar-checkout`, `unloop-polar-checkout`,
   `photoread-polar-checkout`.
4. **Supabase Auth: leaked-password protection** (пункт 10). Проверено чтением
   конфига 07.08.2026: `password_hibp_enabled = false`. Включается одним PATCH
   на `/v1/projects/ncfpxetzmeeqxgqidosj/config/auth` c
   `{"password_hibp_enabled": true}` (или тумблером в дашборде). Looplore
   passwordless, так что для него почти неактуально — включаем, потому что
   проект общий с CRM.

**Порядок применения важен:** миграции и функции — вместе с фронтом. Старый
фронт против новой БД: `state.balance` придёт `undefined` → `stateUnlocks`
упадёт на `undefined >= 95` → пейволл вместо анлока у части покупателей. Новый
фронт против старой БД безопасен (`covered` просто `false`, работает точный
баланс). Значит: **сначала миграции, потом Pages** — либо всё одним окном.

**Смоук после деплоя:**
- анонимная сессия квиза/фото → пейволл виден, `credits_session_state` без
  `balance`, с `covered:false`;
- свой клеймленный `?s=` в приватном окне → шаг почты с текстом «сохранён в
  аккаунте», ввод своей почты → письмо → по ссылке результат открывается;
- свой `?t=&ts=` из кабинета подписанным → тест открывается как раньше;
- чат по своему разбору → история видна; она же по чужому UUID — пустая;
- покупка пака → баланс и анлок как раньше (это трогает `covered`-путь).
