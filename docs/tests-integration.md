## Как продолжить в новой сессии

Всё, что нужно знать, лежит в файлах — переписка не нужна. Читать: этот документ (свой этап + карту), `docs/tests-catalogue.md` (что взято и почему), `docs/tests-scoring-semantics.md` (если трогаешь скоринг).

Промежуточная папка `tools/tests-import/out/` **не хранится в git** и пересоздаётся из исходника. Без неё `npm run tests:verify` упадёт: golden-фикстуры лежат именно там. Восстановление:

```bash
git clone https://github.com/nekitaasiankungfu/tests_app.git /tmp/tests_app
node tools/tests-import/extract.mjs --src /tmp/tests_app
node tools/tests-import/apply-scale-map.mjs
node tools/tests-import/reference-scoring.mjs
npm run tests:verify
```

Готовый контент в `src/content/tests/` в git есть, так что для работы над UI или текстами исходник не нужен — только для пересборки контента (`npm run tests:build`) и для сверки движка.

Прочее состояние: в worktree выполнен `npm install`; дев-сервер поднимается через `.claude/launch.json` (конфигурация `unloop-dev`), тесты открываются на `/tests`.

## Как пользоваться этим документом

Каждый этап — **отдельная сессия**. Сессия начинается с чтения своего брифа и только перечисленных в нём входов; всё остальное читать не надо, это прямая защита от переполнения контекста. Результат сессии — **файл в репозитории**, а не знание в переписке: следующая сессия опирается на артефакт предыдущей и не нуждается в её истории.

Если этап не помещается в сессию — он дробится по своему же принципу (по тестам, по категориям), а не растягивается.

## Э1 — Каталожный триаж ✅ выполнено

Результат: **`docs/tests-catalogue.md`** — вердикт по каждому из 47 тестов и предложенный запускной набор из семи (`text_conflict_communication`, `attachment_styles_v1`, `friendship_red_flags_v1`, `love_languages_v1`, `toxic_patterns`, `ipip_big_five`, `sixteen_types`; 312 вопросов, 70 результатов).

Долг по шкалам у этого набора — 53 фантомные шкалы вместо 532, и 137 из 162 мёртвых ссылок приходятся на один `toxic_patterns`. Плюс всплыло требование к схеме: фактор может кодироваться в **ответе**, а не в вопросе, и сценарные вопросы — отдельный тип карточки. Оба пункта — вход в Э4.

Бриф этапа сохранён ниже как образец для повторного прогона, если набор будут пересматривать.

### Бриф

**Зачем первым.** Отбор радикально сокращает всю последующую работу. Мёртвые весовые ссылки: все 47 тестов → 532 фантомные шкалы (23% ссылок); ядро из 9 тестов про отношения → 70 шкал (11%). Чинить реестр имеет смысл только под отобранный набор, иначе семикратно лишняя работа.

**Вопрос на решение:** какие тесты идут в запуск, какие во второй эшелон, какие не берём вообще.

**Входы (и только они):**
- `tools/tests-import/out/audit.json` — состояние каждого теста
- `tools/tests-import/out/stubs.json` — каталог, длины, категории
- `tools/tests-import/out/tests/<id>.json` — **выборочно**: по 5–8 вопросов и один профиль на кандидата, не весь файл
- предварительный триаж из истории: ядро — attachment_styles, text_conflict_communication, friendship_red_flags, love_languages, romantic_potential, relationship_compatibility, toxic_patterns, love_profile

**Работа.** По каждому кандидату — пять срезов:
1. качество вопросов: конкретность, различимость вариантов, нет ли ваты;
2. **риск копирования**: не воспроизводит ли пункты защищённых инструментов (BDI/PHQ, Thomas-Kilmann TKI, Fisher TI, Chapman Love Languages, MBTI). Проверять формулировками, а не названием;
3. попадание в нишу Looplore (отношения, паттерны, самоузнавание);
4. длина против конверсии: 90 вопросов `motivational_strategies` — заведомо не первый экран;
5. техсостояние из аудита: веса, профили, факторы.

**Выход:** `docs/tests-catalogue.md` — таблица «взять / доработать / переписать / не берём» с обоснованием на каждый тест, зафиксированный запускной набор (ориентир — 6–8 тестов) и для каждого взятого список того, что именно чинить.

**Критерий выхода:** запускной набор согласован основателем.

**Гигиена контекста:** не читать Dart-исходники, не читать тесты целиком, не грузить те, что уже отсеяны.

## Э2 — Нормализация реестра шкал ✅ выполнено

Результат: **`tools/tests-import/scale-map.json`** — 51 алиас (59 весов с переворотом знака) и 2 новые шкалы. Применяется скриптом:

```bash
node tools/tests-import/apply-scale-map.mjs
```

Мёртвых ссылок в запускном наборе — **0**, ничего не выброшено, конфликтов знака при слиянии нет. Реестр 195 → 197 шкал. Отчёт — `out/SCALE_MAP.md`, нормализованные веса — `out/weights-normalized/`.

Принцип, по которому принимались решения: алиас к существующей шкале везде, где есть разумная цель; новая шкала — только если конструкт правдоподобно встретится и в других тестах. Шкала, которую использует ровно один тест, не даёт ничего сквозному профилю, ради которого слой и существует. Поэтому `gaslighting`, `reality_distortion` и `emotional_blackmail` ушли в `manipulation`, а не завели три новые записи.

Два решения, которые стоит помнить при правках карты:
- **знак сохраняется**, а `invert: true` его переворачивает, когда цель — противоположный полюс (`external_locus_of_control` → `self_efficacy`). В исходнике 68 отрицательных весов только в `toxic_patterns` — это инверсный вклад, а не ошибка;
- **при слиянии берётся более сильный вклад, а не сумма.** Коллизии возникают из схлопывания синонимов: `gaslighting` + `reality_distortion` + `manipulation` на одном вопросе — это один сигнал под тремя именами, сумма утроила бы его. Веса исходника доходят до ±1.5 и намеренно не обрезаются.

Для второго эшелона карта не заполнена: там остаётся 479 шкал. Расширять по мере подключения тестов.

### Бриф

**Проблема.** Веса ссылаются на осмысленные конструкты, которых нет в реестре 195: `conscientiousness` (65 ссылок в 13 тестах), `openness` (54), `neuroticism` (39). В реестре есть `dutifulness` и `self_discipline`, но нет самой «Добросовестности». То есть чинить надо словарь, а не 11 тысяч весов.

**Входы:** `out/scales.json`, `out/weights/<только отобранные>.json`, `docs/tests-catalogue.md`.

**Работа.** Отсортировать фантомные шкалы по частоте и разнести на три корзины:
- **алиас** — синоним существующей шкалы (`self_confidence` → `self_efficacy`);
- **новая** — конструкт нужен и в реестре его правда нет (`conscientiousness` как родитель для `dutifulness`/`order`/`self_discipline`);
- **шум** — слишком узкое или единичное; вес выбрасывается вместе со ссылкой.

Скрипт предлагает по строковой и семантической близости, решение принимается вручную по убыванию частоты — верхние 20% шкал закрывают больше половины ссылок.

**Выход:** `tools/tests-import/scale-map.json` (алиасы + новые шкалы + список выброшенного) и прогон аудита с нулём мёртвых ссылок по запускному набору.

**Критерий выхода:** 0 мёртвых ссылок в отобранных тестах; каждая новая шкала имеет ru/en название и родителя.

**Объём:** при ядре из 9 тестов — около 70 шкал, одна сессия. Если набор шире 15 тестов — дробить по категориям.

## Э3 — Семантика скоринга оригинала ✅ выполнено

Результат: **`docs/tests-scoring-semantics.md`** + эталонная реализация `tools/tests-import/reference-scoring.mjs`, которая генерирует golden-фикстуры:

```bash
node tools/tests-import/reference-scoring.mjs
```

Скоринг разделён на два независимых слоя: факторы теста (из них выбирается профиль) и сквозные психологические шкалы (кормят сводный портрет). Слой шкал в оригинале написан аккуратно и переносится как есть. В слое факторов найдены два дефекта, оба исправляются:

- **`maxQuestionScore` задан таблицей констант по id теста**, 13 тестов из 43 в неё не попали и считаются от 5 при реальной шкале 0–4. Из запускного набора это `toxic_patterns`, и следствие проверяемое: потолок 80%, а профиль `severe_toxicity` требует больше 80 — он недостижим ни при каком наборе ответов;
- **обратные вопросы не инвертируются** нигде, кроме `ipip_big_five` и `love_profile`: 22 теста, 247 вопросов. Из набора затронут `friendship_red_flags_v1`.

Числа нашего движка после исправлений намеренно не совпадут с Flutter-приложением. Сверяться надо с фикстурами.

Отдельная находка для Э4: **выбор профиля живёт в Dart-коде, а не в данных** — экстрактором его не достать. Форм две (порог по среднему и цепочка правил по факторам), обе описываются данными; правила по семи взятым тестам переносятся вручную.

### Бриф

**Зачем.** Прежде чем писать движок на TS, надо знать, как считает оригинал — иначе получим правдоподобные, но другие результаты, и все профили поедут.

**Входы:** `lib/services/test_service.dart`, `lib/services/profile_service.dart`, `lib/services/summary_service.dart` (первые ~300 строк), по одному примеру на каждый тип скоринга.

**Работа — задокументировать:**
- нормализация сырых баллов в проценты по фактору, `maxQuestionScore` (он разный: 4 и 5, и это уже было источником багов);
- обработка `isReversed`;
- `determineProfile` — как проценты по шкалам превращаются в профиль;
- частные схемы: ипсативная (`career_compass`, парные сравнения), бинарная (`cognitive_ability`), накопительная по чертам (`visual_micro_tests`), сценарная (`text_conflict_communication`);
- накопление в иерархические шкалы и биполярная сборка типа личности.

**Выход:** `docs/tests-scoring-semantics.md` + golden-фикстуры: набор ответов → ожидаемый результат, минимум по трём тестам разных типов.

**Критерий выхода:** фикстуры сняты с оригинала (прогоном или ручным расчётом по коду), а не придуманы.

**Гигиена:** сессия только про код скоринга. Не читать данные тестов.

## Э4 — Канонический формат и движок ✅ выполнено

Результат:

| Что | Где |
|---|---|
| Схема теста | `src/tests/types.ts` |
| Движок скоринга | `src/tests/engine.ts` |
| Каталог и ленивый загрузчик | `src/tests/registry.ts` |
| Правила выбора профиля | `tools/tests-import/profile-rules.json` |
| Сборка контента | `npm run tests:build` |
| Сверка с фикстурами | `npm run tests:verify` |
| Готовый контент | `src/content/tests/*.json` (7 тестов, ~660 КБ) |

**Сверка проходит: 24 из 24 фикстур, расхождений ноль.** Проект типизируется чисто (`tsc --noEmit`).

Главное свойство схемы: **движок ветвится по режиму скоринга, а не по id теста**. Режимов три — `likert`, `answer_factor` (стиль закодирован в выбранном варианте) и `bipolar`. Добавление теста = положить JSON и правила профиля; в `.ts` не меняется ничего. Для сравнения, в оригинале на каждый тест приходилось восемь точек ручной интеграции и ветка по id в пяти сервисах.

Правила выбора профиля перенесены вручную по всем семи тестам, три формы: порог по среднему, цепочка условий по факторам и ранжирование с комбинациями (love_languages: топ-1 против топ-2 плюс разброс). Условия — данные вида `["secure", ">", 70]`, где операнд может быть числом, другим фактором или производным `@avg` / `@range` / `@top1` / `@diff12`.

Что всплыло по ходу:

- **веса сценарного теста лежат по фактору, а не по вопросу** — 4 полных набора на 4 стиля, и это правильная форма для `answer_factor`: выбор варианта вносит вклад выбранного стиля целиком. Первая версия конвертера искала их по вопросу и ложно отрапортовала «20 вопросов без весов»;
- **третий дефект оригинала** — часть весов не доезжает до пофакторного расчёта, см. `docs/tests-scoring-semantics.md`. Нашёлся именно на сверке движка с фикстурами, ошибка была в эталоне Э3, фикстуры перегенерированы;
- **буквы биполярного кода нельзя выводить из названий полюсов**: `intuition` дало бы I вместо N. В данных они заданы явно;
- **ничьи в биполярных парах** уходят в первый полюс: при полностью одинаковых ответах получается ESTJ. На реальных ответах ничьи почти не встречаются, но помнить стоит.

Что осталось хвостами:

- в `src/content/tests/sixteen_types.json` сейчас лежат английские названия типов, **восемь из которых дословно совпадают с прозвищами 16personalities**. Контент нигде не опубликован, но переименовать нужно до Э6 — это работа Э8;
- у 16 типов заполнены название, описание, сильные стороны и зоны развития; секции `whyThisProfile`, `tryToday`, `inspiringConclusion` пустые — тоже Э8.

### Бриф

**Принцип.** У оригинала 8 точек ручной интеграции на каждый новый тест, и это дало 12 багов на одном DISC. В нашей версии добавление теста = положить JSON, ноль правок кода.

**Э4a — схема и трансформер.** `src/tests/types.ts` (единая форма теста) + скрипт `out/` → `content/tests/*.json` с применением `scale-map.json`. Ипсативные и сценарные тесты укладываются в ту же схему через поле стратегии скоринга, а не через отдельный код.

**Э4b — движок.** `src/tests/engine.ts`: ответы → баллы по факторам → проценты → профиль → вклад в шкалы. Прогон golden-фикстур из Э3.

**Критерий выхода:** движок воспроизводит фикстуры Э3; добавление нового теста не требует правок в `.ts`.

## Э5 — Слой данных ✅ написан, не применён

Результат: `supabase/migrations/20260727130000_psych_tests.sql` и клиентский слой `src/lib/tests.ts`. **Миграция в прод не применялась** — ждёт отдельного «го», как и требует правило по деньгам и деплоям.

Одна таблица `looplore_test_sessions` и шесть RPC. Модель доступа скопирована с существующих воронок: клиент чеканит UUID сессии, хранит в localStorage, и владение этим UUID и есть право на чтение и запись строки. RLS включён, политик нет, всё идёт через security-definer функции — как в `credits_foundation`.

| RPC | Кому | Зачем |
|---|---|---|
| `test_session_save` | anon | Автосохранение ответов по ходу теста |
| `test_session_complete` | anon | Завершение: ответы + результат |
| `test_session_get` | anon | Чтение сессии по ссылке |
| `test_session_claim` | authenticated | Привязать сессию к аккаунту после шага email |
| `test_scale_profile` | authenticated | Сводный портрет по шкалам |
| `test_my_sessions` | authenticated | Список пройденных тестов |

Три решения, которые стоит помнить:

- **Сырые ответы — источник истины.** Результат хранится рядом для дешёвого чтения, но любое изменение весов или правил профиля можно переиграть по ответам, не прося никого перепроходить. Поле `engine_version` помечает, каким набором правил посчитано.
- **`scale_totals` хранит `[взвешенная сумма, сумма весов]` по каждой шкале, а не готовые проценты.** Это достаточные статистики: сквозной профиль складывает их и делит один раз в конце. Если усреднять готовые проценты, тест из 24 вопросов будет весить столько же, сколько тест из 80. Ради этого движок в Э4 научился отдавать `scaleTotals` отдельно от `scaleScores`.
- **Ретейки не удваиваются.** В сводный профиль идёт только последняя завершённая попытка каждого теста (`distinct on (test_id)`).

Что осознанно не сделано и что об этом надо знать:

- **Результат считается на клиенте и присылается готовым.** Сервер его не пересчитывает. Это осознанно: результат теста сейчас ничего не открывает и не тратит кредиты, поэтому подделка вредит только её автору. Когда в Э7 на результат сядет платный разбор, пересчёт на сервере станет обязательным — сырые ответы для этого уже лежат.
- **Анонимная запись не ограничена по частоте.** Тот же профиль риска, что у существующих воронок; при появлении спама лечится троттлингом на уровне функции.
- **SQL нигде не исполнялся.** Локального Postgres нет, на прод без «го» не пойду. Проверить можно на ветке Supabase перед применением.

### Бриф

**Входы:** `supabase/migrations/20260727120000_credits_foundation.sql` (конвенции проекта: префикс `looplore_`, RLS), `src/lib/credits.ts`.

Таблицы: каталог тестов, сессии прохождения, сырые ответы, накопленный профиль пользователя по шкалам. Ответы хранятся сырыми — это позволяет пересчитать всё задним числом после правок весов. Пересчёт — на сервере.

**Критерий выхода:** миграция применена на ветке, RLS закрывает чужие сессии, пересчёт идемпотентен.

Проверено в браузере на дев-сервере: каталог, сценарные карточки, прохождение до конца, результат, ретейк, оба языка. Ошибок в консоли нет, `tsc --noEmit` и `npm run build` чисты.

**Каждый тест собирается в отдельный чанк** — от 40 до 80 КБ, ни один не попадает в основной бандл; сам `TestsApp` весит 27 КБ. Ленивый загрузчик из Э4 работает как задумано.

Решения по ходу:

- **Маршрут — `/tests?t=<id>`, а не `/tests/<id>`.** Сайт раздаётся статикой, и путь с сегментом потребовал бы правила перезаписи на хостинге. Запрос не требует ничего, и это тот же приём, что уже используется для `?s=` в квизе.
- **Биполярный тест показывает не факторы, а баланс полюсов.** У `sixteen_types` `factorIds` не привязаны ни к одному вопросу, так что разбивка по ним дала бы четыре честных на вид нуля. Вместо этого выводятся пары: «Экстраверсия ↔ Интроверсия — 40%».
- **Названия факторов подключены из исходника** (`getFactorNames`), иначе в русском интерфейсе висели бы сырые `passive_aggression`. Для сценарного теста их в исходнике нет — написаны свои.
- Ответы дублируются в localStorage, поэтому перезагрузка посреди теста возвращает на первый неотвеченный вопрос, а не в начало. Всё работает и при выключенном Supabase: скоринг локальный, сервер только запоминает.

Проверка, ради которой всё и затевалось: пройдя `toxic_patterns` ответом «Постоянно» на все 48 вопросов, получаем профиль **«🚨 Крайне токсичные отношения»** — тот самый, который в оригинальном приложении был недостижим из-за дефекта с максимумом (Э3). Исправление подтверждено сквозь весь стек.

Хвосты в Э8: этот профиль сейчас говорит про «эмоциональное насилие» без всякого смягчения, и теперь его реально можно получить — тон и блок поддержки нужны до запуска.
